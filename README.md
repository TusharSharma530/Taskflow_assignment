# TaskFlow

A lightweight, full-stack, Trello-style task board. Tasks are organised into
columns (To Do → In Progress → Done), and every change is persisted to a
MySQL database through a small Express + React application.

This project is a take-home engineering exercise. It prioritises **working core
functionality, real database persistence, backend validation, and tests** over
visual polish.

---

## Tech stack

| Layer      | Technology                                                        |
| ---------- | ----------------------------------------------------------------- |
| Frontend   | React 18, TypeScript, Vite                                         |
| Backend    | Node.js, TypeScript, Express 4                                     |
| Database   | MySQL 8 via [mysql2](https://github.com/sidorares/node-mysql2) |
| Testing    | Vitest (test runner), Supertest (HTTP assertions)                  |
| Tooling    | npm workspaces, `concurrently`                                     |

The database layer uses raw, parameterized SQL through `mysql2` — no ORM. This
deliberately exercises real SQL skills (joins, aggregation, ordering, foreign
keys, check constraints) rather than hiding them behind a query builder.

---

## Features

Implemented:

- Board view with three columns: **To Do**, **In Progress**, **Done**
- Create, edit, and delete tasks (with delete confirmation)
- Move tasks between columns via a dropdown
- Priority badges (**LOW** / **MEDIUM** / **HIGH**) with color coding
- Priority filter (All / Low / Medium / High)
- **Task counts per column** (stretch goal C) — driven by the required
  "task count per column" SQL query
- Full backend validation with consistent JSON errors
- Loading states, disabled buttons while saving, empty states, error banners
- `npm run dev` starts both the API and the Vite dev server together
- Seed script that creates a realistic demo board

Not implemented (deliberately out of scope): authentication, teams,
drag-and-drop, server-side search.

Architecture follows a straightforward vertical slice:

```text
route → controller → service → repository → database
```

The repository layer is the only place SQL lives. Controllers validate input,
services enforce business rules (e.g. "you can only move a task to a column on
the same board"), and repositories read/write data using parameterized queries.

## Database schema

The authoritative schema lives in [`database/schema.sql`](database/schema.sql).

```text
Board
  └── Columns (board_id → boards.id)
        └── Tasks (column_id → columns.id)
```

- Every table has an auto-increment integer primary key.
- `columns.board_id` and `tasks.column_id` are foreign keys with
  **ON DELETE CASCADE** (see Decisions below).
- Required fields are `NOT NULL`.
- `tasks.priority` is restricted to `LOW | MEDIUM | HIGH` by a `CHECK`
  constraint, and defaults to `MEDIUM`.
- A task's status is **not** stored redundantly — its column membership *is*
  its status.
- Timestamps are UTC (`DATETIME(3)`), generated by the database at insert
  time (`UTC_TIMESTAMP(3)`). They round-trip to ISO-8601 strings over the API.
- Tables use the **InnoDB** engine, so foreign keys are always enforced.

## Setup

Requirements: **Node.js 20+** (developed against Node 24), npm, and a running
**MySQL 8** instance.

From a fresh clone:

```bash
git clone <your-repo-url> taskflow
cd taskflow
cp .env.example .env     # then set DB_PASSWORD (and DB_NAME if you prefer)
npm install
npm run seed             # optional: creates/resets the demo board
npm run dev
```

`npm run dev` starts both servers via `concurrently`:

- backend API → <http://localhost:3000> (health check: `GET /api/health`)
- frontend SPA → <http://localhost:5173> (proxies `/api` to the backend)

The backend creates the configured database (if missing), applies the schema,
and seeds the demo board on first start — so a fresh clone never appears empty.
To reset the database to the demo state at any time:

```bash
npm run seed
```

Other useful scripts:

```bash
npm test            # run backend tests (also: npm run test:watch)
npm run build       # type-check + production-build the frontend
```

### Environment variables

Copy `.env.example` to `.env` and set at least `DB_PASSWORD`:

```bash
cp .env.example .env
```

## API

All endpoints expect JSON and respond with JSON.

### Boards

**`GET /api/boards`** — list boards

```json
[{ "id": 1, "title": "TaskFlow Demo Board", "createdAt": "..." }]
```

**`GET /api/boards/:boardId`** — board with its columns and tasks

```json
{
  "id": 1,
  "title": "TaskFlow Demo Board",
  "columns": [
    {
      "id": 1,
      "title": "To Do",
      "position": 1,
      "tasks": [
        { "id": 3, "title": "Write tests", "description": "...", "priority": "HIGH", "createdAt": "..." }
      ]
    }
  ]
}
```

**`GET /api/boards/:boardId/column-counts`** — task count per column (Query 1)

```json
[
  { "columnId": 1, "columnTitle": "To Do", "taskCount": 2 },
  { "columnId": 2, "columnTitle": "In Progress", "taskCount": 1 }
]
```

### Tasks

**`POST /api/tasks`** — create a task. `title` is required and cannot be empty;
`priority` defaults to `MEDIUM`; the column must exist.

```json
// request
{ "columnId": 1, "title": "Create API", "description": "Build the REST API", "priority": "HIGH" }

// 201 response → the created task
{ "id": 6, "columnId": 1, "title": "Create API", "description": "Build the REST API", "priority": "HIGH", "createdAt": "..." }
```

**`PUT /api/tasks/:taskId`** — update `title`, `description` and/or `priority`.

```json
{ "title": "Updated title", "description": "Updated description", "priority": "LOW" }
```

**`DELETE /api/tasks/:taskId`** — delete a task.

```json
{ "message": "Task deleted" }
```

**`PATCH /api/tasks/:taskId/move`** — move a task to another column.

```json
{ "columnId": 2 }
```

### Errors

Errors use one consistent shape with an `error` field:

```json
{ "error": "Task title is required" }
```

| Status | Meaning                                             |
| ------ | --------------------------------------------------- |
| `400`  | Validation failed (bad input, unknown column, etc.) |
| `404`  | Resource not found (task, board, unknown route)     |
| `500`  | Unexpected internal error                            |

Validation errors include: empty/whitespace title, invalid priority
(anything other than `LOW`/`MEDIUM`/`HIGH`), non-numeric ids, missing comment
target columns, and moving a task to a column on a different board.

## Testing

```bash
npm test
```

Runs Vitest + Supertest against the **`taskflow_test` MySQL database**. Every
test connects to a fresh pool, reseeds known data (which resets all tables), and
runs in complete isolation from the development database. No running server is
required — the Express app is created in-process per test.

What is covered:

- **`tests/tasks.api.test.ts`** — create/update/delete/move via the HTTP API,
  including: empty and missing titles → `400`; invalid priority → `400`;
  nonexistent task → `404`; nonexistent column → `400`; moving persists the new
  `column_id`; consistent JSON error shapes; malformed JSON → `400`.
- **`tests/boards.api.test.ts`** — list/get board, board shape, `404` for
  unknown boards, and the column-counts endpoint (Query 1).
- **`tests/repositories.test.ts`** — proves both required SQL queries against
  known data, repository CRUD, and **database integrity**: the `priority`
  `CHECK` constraint, both foreign keys, `ON DELETE CASCADE`, and that InnoDB
  foreign-key enforcement is active.

## Database queries

The two queries the assignment requires are implemented in the repository layer.

### 1. Task count per column `backend/src/repositories/board.repository.ts`

```sql
SELECT
    c.id          AS columnId,
    c.title       AS columnTitle,
    COUNT(t.id)   AS taskCount
FROM columns c
LEFT JOIN tasks t ON t.column_id = c.id
WHERE c.board_id = ?
GROUP BY c.id, c.title, c.position
ORDER BY c.position, c.id;
```

The `LEFT JOIN` keeps columns with zero tasks in the result. Verified by the
"task count per column" tests (including a column with no tasks and isolation
between boards).

### 2. Tasks by priority, newest first `backend/src/repositories/task.repository.ts`

```sql
SELECT
    t.id,
    t.title,
    t.description,
    t.priority,
    t.created_at AS createdAt,
    t.column_id   AS columnId
FROM tasks t
WHERE t.priority = ?
ORDER BY t.created_at DESC, t.id DESC;
```

Ordering is done in SQL (with `id DESC` as a stable tie-breaker), not in
JavaScript. Verified by the "tasks by priority" tests against hand-inserted
timestamps.

Both queries are also exercised in the live API: Query 1 backs the column-counts
endpoint, and Query 2 is unit-tested at the repository layer.

## Decisions / assumptions

Reasonable assumptions made while building:

- **One demo board.** Authentication, multi-team and multi-board management are
  out of scope. The frontend loads the first board returned by `GET /api/boards`.
- **`ON DELETE CASCADE` for both foreign keys.** Deleting a board removes its
  columns; deleting a column removes its tasks. This is the least surprising
  behaviour for a project-board data model and keeps the UI consistent. (A
  `RESTRICT` variant would require explicit cleanup everywhere; a cascade fits
  this small, single-board context.)
- **A task's column represents its status.** No redundant `status` column.
- **Priority defaults to `MEDIUM`** when omitted; an explicitly invalid value is
  rejected with `400`.
- **`created_at` is generated by the backend** (the MySQL default). The client
  cannot set it.
- **Tasks can only move to a column on the same board.** The service verifies
  the target column exists *and* shares the task's board.
- **Column membership proves existence on create/move.** Referential integrity
  is additionally enforced by the database foreign keys.
- **Filtering is client-side.** The frontend filters the already-loaded board
  data by priority (the assignment explicitly allows this for board-level UI).
  The database-level "tasks by priority" query still exists and is tested.
- **Stretch goal chosen: task counts (Option C).** Displayed in each column
  header and sourced from the required count query. Only one stretch goal was
  implemented to avoid compromising core requirements.

## What I would improve

Given more time, without changing the scope of this exercise:

- **Drag-and-drop** between columns (native HTML5 DnD or `@dnd-kit`), with the
  dropdown retained as a fallback.
- **Pagination / virtualization** for boards with many tasks.
- **Optimistic updates** on the frontend for snappier interactions.
- **Server-side search** with an indexed `LIKE`/FTS query.
- **Task ordering** within columns (e.g. manual sort order via a `position`
  column on tasks).
- **Stronger accessibility** (focus trapping in the modal, ARIA live regions,
  keyboard navigation for cards).
- **Deployment / CI** (Dockerfile, GitHub Actions running lint + tests).
- **Richer task model** — due dates, labels, assignees, subtasks.

## What I learned

The most interesting part was migrating the persistence layer from SQLite's
synchronous driver to MySQL's async connection pool (`mysql2`). That touched
every layer: repositories, services, controllers (via an `asyncHandler` wrapper
so rejected promises reach Express's error middleware), the seed logic (now a
transactional, child-first delete with an `AUTO_INCREMENT` reset), and the
`created_at` round-trip — MySQL stores `DATETIME(3)` as `YYYY-MM-DD HH:MM:SS.mmm`
while the API exposes ISO-8601 UTC strings, so a small converter keeps the two in
agreement. Testing moved from an in-memory SQLite file to a dedicated
`taskflow_test` database with sequential test files, which forced the schema
(and its foreign keys) to genuinely enforce integrity over a real engine.
